# Compute Current — AI Infrastructure Intelligence

[www.computecurrent.com](https://www.computecurrent.com) publishes short, source-linked Korean briefs on AI infrastructure — data centers, power and grid, chips and memory, cloud capacity and policy — for operators, investors and infrastructure strategists. Every brief carries its source link and an expert lens; numbers and names are checked against the source before publication.

## How it works

| Part | What it does |
|---|---|
| `packages/pipeline` | Runs on GitHub Actions (`.github/workflows/pipeline.yml`, schedule `45 15,23,7 * * *` UTC = 00:45 / 08:45 / 16:45 KST): ingest the active RSS/Atom and index sources (`config/sources.yaml`) → normalize and dedupe → score and select (`config/scoring.yaml`) → generate a Korean `news_brief` with Claude (`prompts/news_brief.md`) → QA gates (`config/qa.yaml`) → image (brand placeholder) → publish to the Supabase `publications` table. Every run writes the run ledger first, ends with a Telegram summary, and an `ops-check` job keeps one alarm issue (`<!-- cc-ops-alarm -->`) in sync. |
| `apps/site` | Astro 7 server output on Vercel (project Root Directory `apps/site`, ISR 300 s). Reads published rows only, so a pipeline failure or an empty database never breaks a deploy. Answers all 136 preserved legacy URLs (200 / 301 / 410) through its routes and a redirects middleware. |
| `packages/shared` | `@cc/shared`: zod schemas, stage and adapter contracts, config loader, feature flags, redacting logger. |

Design and decisions: `docs/adr/`, `docs/architecture/target.md`, `docs/architecture/contracts.md`. Current state: `docs/STATUS.md`.

## Configuration (names only — never commit values)

- **Site (Vercel Production env):** `SITE_DATA_SOURCE=supabase`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SITE_INDEXABLE`, optional `PUBLIC_ADSENSE_CLIENT` (serves `/ads.txt`).
- **Pipeline (GitHub Actions secrets):** `ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `SUPABASE_PROD_URL` + `SUPABASE_PROD_SERVICE_ROLE_KEY` (production), `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` (staging); optional `OPENAI_API_KEY`, `CC_REVALIDATE_TOKEN`. Production writes also need `CC_ALLOW_PRODUCTION_PUBLISH=true`, which `pipeline.yml` sets only for scheduled runs (and a dispatch with `publish_target=production`).

## Deployment and rollback

- Every push to `main` redeploys production (Vercel project `ai-news-portal`). The site build reads no content (ADR-005); a change that breaks the `apps/site` build is a service impact.
- Verify a deployment with the `rebuild-ci.yml` workflow_dispatch input `verify_base_url=https://www.computecurrent.com` (136/136 expected) and `GET /healthz`.
- Rollback and incident procedures: `docs/runbook.md` (Vercel Instant Rollback first; `legacy-final` tag as the last resort).

## Analytics and ads

AdSense and GA4 loaders were not carried into `apps/site`. `/ads.txt` is served from `PUBLIC_ADSENSE_CLIENT`; GA4 collection stopped at the cutover (accepted 2026-10-31) and bringing it back with a consent banner is an open decision.

## Local development

The site and pipeline are npm workspaces (`apps/site`, `packages/shared`, `packages/pipeline`); see `docs/adr/ADR-001-repo-structure.md`, `docs/architecture/target.md` and `docs/STATUS.md`. Production serves `apps/site` (Vercel Root Directory) since the Phase 5 cutover.

```bash
npm ci                                   # installs the workspace dependencies (Node 22.x)
npm run v2:typecheck                     # tsc (packages/*) + astro check (apps/site)
npm run v2:test                          # node --test across the three workspaces, fixtures only
npm run v2:build                         # astro build for apps/site (SITE_DATA_SOURCE=empty works)
npm run v2:pipeline -- run --dry-run --replay --fixture sample --json
npm run v2:pipeline -- run --dry-run --live --stage ingest --json   # Phase 3a: real feeds, memory ledger only
CC_FLAG_STAGES_NORMALIZE=true npm run v2:pipeline -- run --dry-run --replay --fixture dedupe --sources fixtures/sources/dedupe.yaml --stage ingest,normalize --json   # Phase 3b: 12 items from 3 wires -> 6 candidates
CC_FLAG_STAGES_NORMALIZE=true CC_FLAG_STAGES_SCORE=true npm run v2:pipeline -- run --dry-run --replay --fixture scoring --sources fixtures/sources/scoring.yaml --stage ingest,normalize,score --json   # Phase 3c: 13 items -> 6 pass -> 2 selected
CC_FLAG_STAGES_NORMALIZE=true CC_FLAG_STAGES_SCORE=true CC_FLAG_STAGES_GENERATE=true npm run v2:pipeline -- run --dry-run --replay --fixture scoring --sources fixtures/sources/scoring.yaml --stage ingest,normalize,score,generate --json   # Phase 3d: 2 selected -> 2 news_brief drafts from recorded replies
CC_FLAG_STAGES_NORMALIZE=true CC_FLAG_STAGES_SCORE=true CC_FLAG_STAGES_GENERATE=true CC_FLAG_STAGES_IMAGE=true npm run v2:pipeline -- run --dry-run --replay --fixture scoring --sources fixtures/sources/scoring.yaml --stage ingest,normalize,score,generate,qa,image --json   # Phase 3f: image stage after QA (QA off → 0 drafts pass, fail-closed)
CC_FLAG_STAGES_NORMALIZE=true CC_FLAG_STAGES_SCORE=true CC_FLAG_STAGES_GENERATE=true CC_FLAG_STAGES_QA=true CC_FLAG_STAGES_IMAGE=true npm run v2:pipeline -- run --dry-run --replay --fixture scoring --sources fixtures/sources/scoring.yaml --stage ingest,normalize,score,generate,qa,image --json   # Phase 3g: 2 drafts -> 26 verdicts -> 1 passes (placeholder image), 1 rejected (UNGROUNDED_NUMBER)
CC_FLAG_STAGES_NORMALIZE=true CC_FLAG_STAGES_SCORE=true CC_FLAG_STAGES_GENERATE=true CC_FLAG_STAGES_QA=true CC_FLAG_STAGES_IMAGE=true CC_FLAG_PUBLISH_TARGET=staging npm run v2:pipeline -- run --dry-run --replay --fixture scoring --sources fixtures/sources/scoring.yaml --stage ingest,normalize,score,generate,qa,image,publish --json   # Phase 3h: the QA-passed draft becomes a publications row in the run's memory DB (published 1, redirects synced 44: 28 × 301 + 16 × 410)
node packages/pipeline/tools/migrate-legacy-publications.ts --dry-run   # Phase 3h: plan the Phase 5 legacy migration (25 preserved URLs -> ready / not_public / missing)
CC_FLAG_STAGES_NORMALIZE=true CC_FLAG_STAGES_SCORE=true CC_FLAG_STAGES_GENERATE=true CC_FLAG_STAGES_QA=true CC_FLAG_STAGES_IMAGE=true CC_FLAG_PUBLISH_TARGET=staging CC_FLAG_NOTIFY_TELEGRAM=true TELEGRAM_BOT_TOKEN=<dummy> TELEGRAM_CHAT_ID=0 npm run v2:pipeline -- run --dry-run --replay --fixture scoring --sources fixtures/sources/scoring.yaml --stage ingest,normalize,score,generate,qa,image,publish --json   # Phase 3i: the run summary (--json summary.text) plus a soft-failed Telegram delivery (NETWORK_DISABLED under --replay)
npm run v2:pipeline -- ops --from <run.json>                              # Phase 3i: ops check on a run dump (Supabase without --from): ok / stale / never / failing, exit 1 when not ok
npm run v2:pipeline -- run --live --trigger dispatch --json               # no --dry-run: writes the Supabase project named by SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY (staging); must be --live; production also needs CC_ALLOW_PRODUCTION_PUBLISH=true and SUPABASE_PROD_*
```

- The pipeline CLI accepts `--stage <name>[,<name>]`, `--dry-run`, `--live`, `--fixture <name>`, `--replay`, `--config`, `--sources`, `--fixtures-dir`, `--trigger`, `--json`, `--log-level`; `pipeline ops [--from <json>]` (Phase 3i) assesses the run ledger; `pipeline review [--run <id> | --status <s>] [--limit <n>] [--window <chars>]` (Phase 4) prints the sample-review dump (drafts, QA verdicts, source excerpts around ungrounded numbers; `.github/workflows/shadow-review.yml` puts it in a step summary); in `pipeline.yml` the `ops-check` job turns its exit code into one GitHub alarm issue (`packages/pipeline/tools/ops-issue-sync.ts`: found by a body marker, written only on a state transition, closed on recovery, `issues: write` on that job only). A fixture run seeds the memory DB from `fixtures/db/<fixture>.json` when present. The normalize (Phase 3b), score (Phase 3c), generate (Phase 3d), qa (Phase 3g) and image (Phase 3f) stages are off by default (`flags.stages.normalize: false`, `flags.stages.score: false`, `flags.stages.generate: false`, `flags.stages.qa: false`, `flags.stages.image: false`); set `CC_FLAG_STAGES_NORMALIZE=true` / `CC_FLAG_STAGES_SCORE=true` / `CC_FLAG_STAGES_GENERATE=true` / `CC_FLAG_STAGES_QA=true` / `CC_FLAG_STAGES_IMAGE=true` to run them. A QA stage that is off passes nothing (fail-closed), so image and publish get no input. The scoring rubric is data in `config/scoring.yaml` (`--scoring <path>`): five axes, weights, thresholds, selection caps and every vocabulary and pattern the engine uses; each scored candidate stores a per-axis reason (`candidates.rubric`, migration `0002_candidates_rubric.sql`); `selection.skip_review_status` (default rejected, pending) keeps a candidate whose news_brief draft for the current prompt was rejected or is held from taking a slot again (`PREVIOUSLY_REJECTED` / `PENDING_REVIEW`). The generate stage (Phase 3d) turns each selected candidate into a Korean `news_brief` draft: the prompt is the versioned file `prompts/news_brief.md` (`--prompts-dir`) whose banned-phrase line is rendered from `config/banned-phrases.yaml` (`--banned-phrases`; the same inventory is matched on every draft and reported as `checks.banned`; the QA rule `BANNED_PATTERN` blocks), the model writes only title, summary, why-it-matters, expert lens and tags while the stage fills the source fields and slug, and `llm.provider` in `config/pipeline.yaml` picks the adapter (`fixture` replays `fixtures/llm/news_brief/<raw_item_id>.json`; `anthropic` calls the Messages API through the run's fetch and needs `ANTHROPIC_API_KEY`; `disabled` fails the stage). Every call is estimated against `budget` before it is made, and each draft records a numeric grounding check and the longest run of words shared with the source (reported by the generate stage, enforced by the QA stage). The image stage (Phase 3f) gives every QA-passed draft an image through a provider chain (`image.provider` then `image.fallback_chain`, always ending in the brand placeholder): the placeholder is a deterministic SVG per publication, `openai` is opt-in (`OPENAI_API_KEY`, priced per image from `image.pricing`, skipped when the run budget cannot cover it), and a placeholder standing in for a configured provider leaves an `IMAGE_MISSING` soft verdict. Generated bytes go to an image store (memory by default, a directory with `--images-dir`), never into the repo. The QA stage (Phase 3g) runs every enabled rule of `config/qa.yaml` (`--qa`) on every draft in the file's order and never stops early: one rule is one file under `packages/pipeline/src/qa/rules/<CODE>.ts` named after the reason code it emits, severities, `auto_pass` and every threshold live only in the config, every verdict is written to `qa_results`, a hard failure rejects the draft (`drafts.review_status: rejected`), a soft failure without `auto_pass` holds it for human review (`pending`), and a rule listed in the config without a file fails the run (`QA_RULE_UNKNOWN`). The publish stage (Phase 3h) is switched by `flags.publish_target` (`none` by default: nothing is written and every candidate is reported as `dry`; `CC_FLAG_PUBLISH_TARGET=staging` writes to the run's database, the memory one under `--dry-run`): a publication is one `publications` row keyed by slug (a re-run updates it in place, a slug taken by another draft follows `publish.slug_conflict`), `config/redirects.yaml` is synced into the `redirects` table, and on-demand ISR revalidation (`publish.revalidate`, off by default, token name only) is reported but never fatal, so publishing never depends on a site build. Source adapters are fixtures unless `--live` swaps in the real RSS/Atom and Epoch index adapters (Phase 3a); A run without `--dry-run` writes Supabase and must be `--live` (`--replay` and fixture runs always need `--dry-run`); `--live` excludes `--replay`, and `--replay` makes every network call throw.
- Live ingest evidence: the `ingest-live-dry-run` job of `.github/workflows/rebuild-ci.yml` (workflow_dispatch with `live_ingest=true`, no secrets) runs the ingest stage against the live feeds and writes the funnel plus a per-source table to the step summary. `config/sources.yaml` (82 rows) was generated once by `packages/pipeline/tools/migrate-legacy-registry.ts` from the legacy registry and is hand-edited from there; a source the pipeline auto-disabled comes back when its `reviewed_at` is later than the auto-disable day.
- Feature flags: `config/pipeline.yaml` (`flags.stages.<stage>`, `flags.publish_target`, `notify.telegram.enabled`) or the environment (`CC_FLAG_STAGES_IMAGE=false`, `CC_FLAG_PUBLISH_TARGET=staging`, `CC_FLAG_NOTIFY_TELEGRAM=true`, `CC_FLAG_LLM_PROVIDER=anthropic` for live runs while the file default stays `fixture`). Unknown flags fail the run. Every finished run ends with the ADR-007 summary in the log and in `--json summary.text`; with Telegram on, the same text goes out once through the Bot API (`TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` by name only; a failed delivery is counted, never a run failure). `.github/workflows/pipeline.yml` is the scheduled runtime (ADR-002), shipped as `workflow_dispatch` only with the cron commented and `--dry-run` fixed until Phase 4; the slots are 00:45 / 08:45 / 16:45 KST (`45 15,23,7 * * *` UTC).
- Site data source: `SITE_DATA_SOURCE=supabase` (`SUPABASE_URL` + `SUPABASE_ANON_KEY`, published rows only), `legacy_json` (maps the legacy reader pages frozen in `fixtures/legacy/`; for local dev and the offline URL parity check, not available in the Vercel function runtime) or `empty`. Unset means `empty`, so a deployment opts in explicitly. `GET /healthz` reports the active source and the published count. Pages are `noindex` until `SITE_INDEXABLE=true`.
- `supabase/migrations/0001_init.sql` and `0002_candidates_rubric.sql` are applied to the staging and production projects; a new migration is a pre-approval item.
- TypeScript runs directly on Node 22 type stripping: erasable syntax only, `.ts` extensions in relative imports, `import type` for types.
